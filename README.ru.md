# CryptoX

**Модульный криптографический SDK для Go — в разработке.**

[English](README.md) · [Português (Brasil)](README.pt-BR.md) · [简体中文](README.zh-CN.md) · [हिन्दी](README.hi.md) · [Русский](README.ru.md)

CryptoX развивается из утилиты шифрования файлов в криптографическую библиотеку общего назначения. Цель — предоставить повторно используемые и пригодные для аудита компоненты шифрования, управления ключами, зашифрованного хранения, идентификации и интеграции с устоявшимися протоколами E2EE, независимо от облачных провайдеров, транспортов, баз данных и прикладных фреймворков.

> **Текущее состояние:** реализованы генерация случайных ключей AES и шифрование файлов в устаревшем формате v1. Этот формат аутентифицирует отдельные блоки, **но не файл целиком**. Удаление последних полных блоков не обнаруживается. Не используйте эту реализацию там, где требуется целостность всего файла. Независимый аудит безопасности и готовность к промышленной эксплуатации не заявляются.

## Зачем изучать CryptoX?

- **Пакеты с конкретными задачами:** импортируйте `keys` и `stream` напрямую, без зависимости от общего пакета утилит.
- **Ограниченное потребление памяти:** файлы обрабатываются блоками до 64 КиБ, без загрузки всего файла в RAM.
- **Минимум зависимостей:** текущая библиотека использует только стандартную библиотеку Go, без CGO, обязательных внешних сервисов и телеметрии.
- **Явное поведение при сбоях:** некорректный ввод и ошибки аутентификации возвращают ошибки; целевой файл публикуется только после успешного завершения операции.
- **Проверяемые инженерные практики:** включены тесты со злонамеренными входными данными, фаззинг, детектор гонок, статический анализ и конфигурация CI.

Сегодня CryptoX подходит для оценки архитектуры, изучения существующего формата и участия в модернизации. Будущие задачи включают защищённые вложения, резервные копии, офлайн-хранение, межсервисное взаимодействие, идентификацию устройств и интеграции E2EE. Это предполагаемые сценарии, а не уже готовые комплексные решения. Проверенных сравнений производительности и гарантий превосходства над другими библиотеками нет.

## Что уже существует?

| Пакет | Доступный API | Поведение |
| --- | --- | --- |
| `keys` | `GenerateKey(size int) ([]byte, error)` | Генерирует ключи AES длиной 16, 24 или 32 байта через `crypto/rand`. |
| `stream` | `EncryptLargeFiles(infile, outfile string, key []byte) error` | Шифрует файл с помощью AES-GCM в устаревший формат v1. |
| `stream` | `DecryptLargeFiles(infile, outfile string, key []byte) error` | Проверяет каждый блок и записывает восстановленный файл; не проверяет его полноту. |
| `stream` | `ValidateEncryptedFile(filename string) error` | Проверяет только заголовок. **Не** проверяет шифротекст и теги. |
| `utils` | Те же четыре устаревшие функции | Устаревший фасад совместимости, делегирующий вызовы `keys` и `stream`. |

Публичные API пока принимают пути к файлам. Публичные API `io.Reader`/`io.Writer`, аутентифицированное завершение потока, HKDF, конверты, защищённое хранилище, идентификация, ratchet-механизмы, защита от повторного воспроизведения, мобильные привязки и постквантовая поддержка **не реализованы**.

Исходный код объявляет Go 1.26 минимальным уровнем совместимости. Для разработки и эксплуатации используйте поддерживаемую версию Go; минимальная совместимость исходников не является рекомендацией по безопасности. Ядро библиотеки не требует CGO, но `go test -race` требует поддерживаемую платформу и инструментарий C.

## Установка

### Локальная рабочая копия

Чтобы попробовать именно описанную здесь реализацию, направьте отдельный демонстрационный модуль на свою рабочую копию CryptoX. Замените `/absolute/path/to/cryptox` настоящим абсолютным путём:

```sh
mkdir cryptox-demo
cd cryptox-demo
go mod init example.com/cryptox-demo
go mod edit -require=github.com/Hangell/cryptox@v0.0.0
go mod edit -replace=github.com/Hangell/cryptox=/absolute/path/to/cryptox
```

Здесь `v0.0.0` — только условная версия в требовании локального модуля, а не заявление о опубликованном релизе. Директива `replace` заставляет Go использовать локальные файлы.

### Удалённый модуль

Внутри существующего модуля Go:

```sh
go get github.com/Hangell/cryptox
```

Команда загружает версию, доступную в удалённом репозитории, **а не неопубликованные локальные изменения**. Убедитесь, что выбранная ревизия содержит `keys` и `stream`: структура пакетов и форматы могут измениться при модернизации. Здесь не заявляется наличие стабильного релиза или успешный текущий результат удалённого CI.

## Пример: создание ключа, шифрование, проверка заголовка и расшифрование

Сохраните следующий код как `main.go` в `cryptox-demo` и выполните `go run .`:

```go
package main

import (
    "bytes"
    "fmt"
    "log"
    "os"
    "path/filepath"

    "github.com/Hangell/cryptox/keys"
    "github.com/Hangell/cryptox/stream"
)

func main() {
    if err := run(); err != nil {
        log.Fatal(err)
    }
}

func run() error {
    // Use disposable data: the v1 format lacks whole-file integrity.
    dir, err := os.MkdirTemp("", "cryptox-demo-*")
    if err != nil {
        return err
    }
    defer os.RemoveAll(dir)

    input := filepath.Join(dir, "message.txt")
    encrypted := filepath.Join(dir, "message.enc")
    restored := filepath.Join(dir, "restored.txt")
    original := []byte("Hello from CryptoX!\n")
    if err := os.WriteFile(input, original, 0o600); err != nil {
        return err
    }

    // Generate a fresh AES-256 key for this file. Never log it.
    key, err := keys.GenerateKey(32)
    if err != nil {
        return err
    }
    if err := stream.EncryptLargeFiles(input, encrypted, key); err != nil {
        return err
    }
    // This checks the header only, not ciphertext integrity.
    if err := stream.ValidateEncryptedFile(encrypted); err != nil {
        return err
    }
    if err := stream.DecryptLargeFiles(encrypted, restored, key); err != nil {
        return err
    }
    recovered, err := os.ReadFile(restored)
    if err != nil {
        return err
    }
    // This comparison checks the demo, not the v1 format's security.
    if !bytes.Equal(original, recovered) {
        return fmt.Errorf("round-trip mismatch")
    }
    fmt.Println("Round trip OK")
    return nil
}
```

Ожидаемый вывод: `Round trip OK`. Пример использует одноразовые тестовые файлы и удаляет их после завершения. Только демонстрация полностью читает небольшой открытый текст для сравнения; библиотека обрабатывает файлы постепенно.

Ключ остаётся в памяти только на время этого запуска. Для постоянных данных приложение должно отдельно обеспечить безопасное сохранение и восстановление ключа: CryptoX пока не предоставляет хранилище ключей. Потеря ключа означает потерю доступа к данным. Не выводите ключи и не добавляйте их в репозиторий; не используйте пароли напрямую как ключи AES. Выработка ключа из пароля не реализована. Для каждого файла v1 используйте новый ключ; API не обеспечивает соблюдение этой политики.

Существующие потребители могут импортировать `github.com/Hangell/cryptox/utils` и вызывать функции с прежними именами. В новом коде используйте специализированные пакеты. Это описание текущей совместимости, а не обещание сохранить устаревшие API при дальнейшей модернизации.

## Границы безопасности и устаревший формат

```text
Header (21 bytes): "SYM1" | version=1 | "AESG" | base nonce (12 bytes)
Record: ciphertext length (uint32 LE) | ciphertext | GCM tag (16 bytes)
Nonce: random prefix (8 bytes) | chunk counter (uint32 LE)
```

Поле длины включает тег GCM. Последние четыре байта nonce в заголовке должны быть нулевыми; каждая запись использует последовательный счётчик. Значения за пределами `uint32` отклоняются, что предотвращает переполнение с возвратом к нулю внутри файла.

- **Принятие неполного файла:** удаление последних полных записей может остаться незамеченным. Пустой файл не содержит тега аутентификации и не позволяет проверить ключ.
- **Неполная аутентификация метаданных:** структура заголовка проверяется, но он не аутентифицируется целиком как ассоциированные данные.
- **Коллизии nonce между файлами:** случайный префикс имеет длину лишь 64 бита. Повторное использование ключа для разных файлов может привести к совпадению префиксов. Проверка счётчика не устраняет этот риск.
- **Публикация файла:** уникальные временные файлы создаются в целевом каталоге с Unix-правами `0600`; перед переименованием данные синхронизируются, а файл закрывается. При ошибке выполняется попытка очистки, целевой файл намеренно не заменяется. Успешная операция может заменить существующий результат; заранее создайте родительский каталог и внимательно выбирайте пути.
- **Ограничения ОС:** используйте доверенный целевой каталог. В Windows необходимы подходящие ACL; атомарность переименования зависит от ОС и файловой системы. Сам каталог не синхронизируется, поэтому сохранность после аварийного завершения не гарантируется. Сбой процесса может оставить временные файлы.
- **Секреты и модель угроз:** Go не гарантирует немедленного стирания памяти. Код не защищает от скомпрометированного процесса/ОС, отката хранилища, повторного воспроизведения или анализа метаданных и не является протоколом E2EE.

Само применение AES-GCM не делает файловый формат безопасным. Новый формат должен явно аутентифицировать метаданные и завершение и пройти соответствующую проверку; эти свойства нельзя приписывать v1 задним числом.

## Архитектура и направление развития

Проект использует модульные и гексагональные принципы: потребители работают с отдельными пакетами; необязательные адаптеры зависят от контрактов ядра; ядро не зависит от инфраструктуры. Интерфейсы вводятся на реальных границах абстракций, а не для каждой функции.

| Планируемый компонент | Ответственность |
| --- | --- |
| `aead` | Аутентифицированное шифрование и управление nonce. |
| Расширение `keys` | Выработка ключей, разделение по назначению, жизненный цикл и интеграция с хранилищем. |
| Замена `stream` | Аутентифицированные кадрирование, метаданные, порядок и завершение. |
| `envelope` | Форматы зашифрованных объектов с явными версиями. |
| `securestorage` | Зашифрованное состояние и необязательные адаптеры хранения. |
| `identity` / `pki` | Идентификация устройств, подписи, учётные данные, сертификаты и проверка доверия. |
| `e2ee` | Адаптеры устоявшихся протоколов сеансов/групп, выбранных по результатам проверки. |

Среди рассматриваемых технологий — ChaCha20-Poly1305, HKDF, X25519, Ed25519, Argon2id, MLS и проверенные постквантовые механизмы. Это кандидаты для оценки, а не доступные возможности или рецепт собственного протокола. CryptoX не будет реализовывать серверы сообщений, регистрацию пользователей, очереди, доставку push-уведомлений или облачную оркестрацию.

## Тесты и CI

Запускайте из репозитория CryptoX. Первый блок использует Make, второй содержит прямые команды, включая анализ уязвимостей:

```sh
make check
make fuzz
```

```sh
go vet ./...
go test -race -count=1 -coverpkg=./... -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
go test ./stream -run='^$' -fuzz=FuzzDecryptV1 -fuzztime=30s -parallel=2
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
```

Тестируются четыре функции `utils`, длины ключей AES, границы блоков, неверные ключи, повреждённые заголовки/длины, изменённые или переставленные блоки, фрагментированные чтения, неполные записи, передача ошибок, очистка временных файлов и сохранение целевого файла. Параллельные сценарии используют независимые файлы. Отдельные тесты явно фиксируют ограничение v1 при усечении. Фаззинг проверяет инварианты при сбоях, а не только отсутствие panic.

[CI workflow](.github/workflows/ci.yml) настроен на push, pull request, ручной и еженедельный запуск. Он определяет задания Linux/Windows/macOS с Go `stable`, дополнительное задание Linux с `oldstable`, артефакты покрытия и JSON, фаззинг и `govulncheck`. Наличие конфигурации не доказывает удалённый успех: проверяйте запуск для своего коммита. Покрытие и успешные тесты не заменяют независимую криптографическую проверку.
