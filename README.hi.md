# CryptoX

**Go के लिए मॉड्यूलर क्रिप्टोग्राफ़िक SDK — विकासाधीन।**

[English](README.md) · [Português (Brasil)](README.pt-BR.md) · [简体中文](README.zh-CN.md) · [हिन्दी](README.hi.md) · [Русский](README.ru.md)

CryptoX एक फ़ाइल एन्क्रिप्शन उपयोगिता से सामान्य उपयोग की क्रिप्टोग्राफ़िक लाइब्रेरी की ओर बढ़ रहा है। इसका लक्ष्य एन्क्रिप्शन, कुंजी प्रबंधन, एन्क्रिप्टेड स्टोरेज, पहचान और स्थापित E2EE प्रोटोकॉल के साथ एकीकरण के लिए पुनः उपयोग योग्य तथा ऑडिट योग्य घटक देना है, जो क्लाउड प्रदाताओं, ट्रांसपोर्ट, डेटाबेस और एप्लिकेशन फ़्रेमवर्क से स्वतंत्र हों।

> **वर्तमान स्थिति:** कोड में यादृच्छिक AES कुंजी निर्माण और पुराने v1 प्रारूप में फ़ाइल एन्क्रिप्शन उपलब्ध है। v1 अलग-अलग डेटा खंडों को प्रमाणित करता है, **पूरी फ़ाइल को नहीं**। यह अंत के पूरे खंड हटाए जाने का पता नहीं लगा सकता। जहाँ पूरी फ़ाइल की अखंडता आवश्यक हो, वहाँ इस कार्यान्वयन का उपयोग न करें। स्वतंत्र सुरक्षा ऑडिट या प्रोडक्शन के लिए तैयार होने का कोई दावा नहीं है।

## CryptoX को क्यों देखें?

- **स्पष्ट जिम्मेदारियों वाले पैकेज:** सामान्य उपयोगिता पैकेज पर निर्भर होने के बजाय सीधे `keys` और `stream` आयात करें।
- **सीमित मेमोरी उपयोग:** पूरी फ़ाइल RAM में लोड करने के बजाय अधिकतम 64 KiB के खंडों में प्रसंस्करण होता है।
- **कम निर्भरताएँ:** वर्तमान लाइब्रेरी केवल Go की मानक लाइब्रेरी का उपयोग करती है; CGO, अनिवार्य सेवाएँ या टेलीमेट्री नहीं हैं।
- **स्पष्ट विफलता व्यवहार:** गलत प्रारूप और प्रमाणीकरण विफलता पर त्रुटि लौटती है; ऑपरेशन सफल होने के बाद ही गंतव्य फ़ाइल प्रकाशित होती है।
- **सत्यापन योग्य इंजीनियरिंग:** प्रतिकूल इनपुट के परीक्षण, फ़ज़िंग, डेटा रेस जाँच, स्थैतिक विश्लेषण और CI कॉन्फ़िगरेशन शामिल हैं।

आज CryptoX का उपयोग आर्किटेक्चर का मूल्यांकन करने, मौजूदा प्रारूप का अध्ययन करने और आधुनिकीकरण में योगदान देने के लिए किया जा सकता है। भविष्य के लक्ष्य सुरक्षित अटैचमेंट, बैकअप, ऑफ़लाइन स्टोरेज, सेवाओं के बीच संचार, डिवाइस पहचान और E2EE एकीकरण हैं। ये प्रस्तावित उपयोग हैं, अभी उपलब्ध पूर्ण समाधान नहीं। अन्य लाइब्रेरी से बेहतर प्रदर्शन की कोई सत्यापित तुलना या गारंटी नहीं है।

## अभी क्या उपलब्ध है?

| पैकेज | उपलब्ध API | व्यवहार |
| --- | --- | --- |
| `keys` | `GenerateKey(size int) ([]byte, error)` | `crypto/rand` से 16, 24 या 32 बाइट की AES कुंजी बनाता है। |
| `stream` | `EncryptLargeFiles(infile, outfile string, key []byte) error` | AES-GCM से फ़ाइल को पुराने v1 प्रारूप में एन्क्रिप्ट करता है। |
| `stream` | `DecryptLargeFiles(infile, outfile string, key []byte) error` | प्रत्येक खंड की जाँच करके पुनः प्राप्त फ़ाइल लिखता है; फ़ाइल की पूर्णता सत्यापित नहीं कर सकता। |
| `stream` | `ValidateHeader(filename string) error` | केवल हेडर जाँचता है। सिफ़रटेक्स्ट या टैग सत्यापित **नहीं** करता। `ValidateEncryptedFile` एक हटाया गया (deprecated) उपनाम है। |
| `utils` | वही चार पुराने फ़ंक्शन | पुरानी संगतता के लिए पदावनत फ़साड, जो `keys` और `stream` को कॉल करता है। |

सार्वजनिक API अभी फ़ाइल पथ लेते हैं। सार्वजनिक `io.Reader`/`io.Writer` API, प्रमाणित स्ट्रीम समापन, HKDF, एनवेलप, सुरक्षित स्टोरेज, पहचान, रैचेट, रीप्ले सुरक्षा, मोबाइल बाइंडिंग और पोस्ट-क्वांटम समर्थन **अभी लागू नहीं हैं**।

स्रोत कोड Go 1.26 को न्यूनतम संगतता स्तर घोषित करता है। विकास और परिनियोजन के लिए अभी अनुरक्षित Go टूलचेन इस्तेमाल करें; न्यूनतम स्रोत संगतता सुरक्षा की अनुशंसा नहीं है। लाइब्रेरी के मूल भाग को CGO नहीं चाहिए, लेकिन `go test -race` के लिए समर्थित प्लेटफ़ॉर्म और C टूलचेन आवश्यक हैं।

## स्थापना

### स्थानीय चेकआउट का उपयोग

यहाँ वर्णित कार्यान्वयन को आज़माने के लिए अलग डेमो मॉड्यूल को अपने CryptoX चेकआउट से जोड़ें। `/absolute/path/to/cryptox` को वास्तविक पूर्ण पथ से बदलें:

```sh
mkdir cryptox-demo
cd cryptox-demo
go mod init example.com/cryptox-demo
go mod edit -require=github.com/Hangell/cryptox@v0.0.0
go mod edit -replace=github.com/Hangell/cryptox=/absolute/path/to/cryptox
```

यहाँ `v0.0.0` केवल स्थानीय मॉड्यूल आवश्यकता का प्लेसहोल्डर है; इसका अर्थ किसी प्रकाशित रिलीज़ का दावा नहीं है। `replace` निर्देश Go को आपकी स्थानीय फ़ाइलें इस्तेमाल करने के लिए कहता है।

### रिमोट मॉड्यूल का उपयोग

पहले से मौजूद Go मॉड्यूल में:

```sh
go get github.com/Hangell/cryptox
```

यह रिमोट रिपॉज़िटरी में उपलब्ध संस्करण डाउनलोड करता है, **अप्रकाशित स्थानीय बदलाव नहीं**। जाँचें कि चुने गए रिविज़न में `keys` और `stream` मौजूद हैं; आधुनिकीकरण के दौरान पैकेज संरचना और प्रारूप बदल सकते हैं। यहाँ स्थिर रिलीज़ या वर्तमान रिमोट CI सफलता का दावा नहीं किया गया है।

## उदाहरण: कुंजी बनाएँ, एन्क्रिप्ट करें, हेडर जाँचें और डिक्रिप्ट करें

नीचे का कोड `cryptox-demo` में `main.go` नाम से सहेजें और `go run .` चलाएँ:

```go
package main

import (
    "bytes"
    "fmt"
    "log"
    "os"
    "path/filepath"

    "github.com/Hangell/cryptox/keys"
    "github.com/Hangell/cryptox/stream"
)

func main() {
    if err := run(); err != nil {
        log.Fatal(err)
    }
}

func run() error {
    // Use disposable data: the v1 format lacks whole-file integrity.
    dir, err := os.MkdirTemp("", "cryptox-demo-*")
    if err != nil {
        return err
    }
    defer os.RemoveAll(dir)

    input := filepath.Join(dir, "message.txt")
    encrypted := filepath.Join(dir, "message.enc")
    restored := filepath.Join(dir, "restored.txt")
    original := []byte("Hello from CryptoX!\n")
    if err := os.WriteFile(input, original, 0o600); err != nil {
        return err
    }

    // Generate a fresh AES-256 key for this file. Never log it.
    key, err := keys.GenerateKey(32)
    if err != nil {
        return err
    }
    if err := stream.EncryptLargeFiles(input, encrypted, key); err != nil {
        return err
    }
    // This checks the header only, not ciphertext integrity.
    if err := stream.ValidateHeader(encrypted); err != nil {
        return err
    }
    if err := stream.DecryptLargeFiles(encrypted, restored, key); err != nil {
        return err
    }
    recovered, err := os.ReadFile(restored)
    if err != nil {
        return err
    }
    // This comparison checks the demo, not the v1 format's security.
    if !bytes.Equal(original, recovered) {
        return fmt.Errorf("round-trip mismatch")
    }
    fmt.Println("Round trip OK")
    return nil
}
```

अपेक्षित आउटपुट: `Round trip OK`। उदाहरण अस्थायी परीक्षण फ़ाइलें बनाता है और अंत में उन्हें हटा देता है। केवल डेमो परिणाम की तुलना के लिए छोटे प्लेनटेक्स्ट को पूरा पढ़ता है; लाइब्रेरी फ़ाइलों को क्रमिक रूप से संसाधित करती है।

कुंजी केवल इस रन के दौरान मेमोरी में रहती है। स्थायी डेटा के लिए एप्लिकेशन को कुंजी अलग से सुरक्षित रखनी और पुनः प्राप्त करनी होगी; CryptoX में अभी कुंजी भंडार नहीं है। कुंजी खोने पर डेटा का उपयोग संभव नहीं रहेगा। कुंजियाँ कभी प्रिंट या कमिट न करें और पासवर्ड को सीधे AES कुंजी न बनाएँ। पासवर्ड से कुंजी व्युत्पत्ति अभी लागू नहीं है। हर v1 फ़ाइल के लिए नई कुंजी इस्तेमाल करें; API इस नीति को लागू नहीं करता।

मौजूदा उपभोक्ता अभी भी `github.com/Hangell/cryptox/utils` आयात कर वही फ़ंक्शन नाम इस्तेमाल कर सकते हैं। नए कोड में विशिष्ट पैकेज अपनाएँ। यह वर्तमान संगतता का विवरण है, भविष्य के आधुनिकीकरण में पुरानी API बनाए रखने का वादा नहीं।

## सुरक्षा सीमाएँ और पुराना प्रारूप

```text
Header (21 bytes): "SYM1" | version=1 | "AESG" | base nonce (12 bytes)
Record: ciphertext length (uint32 LE) | ciphertext | GCM tag (16 bytes)
Nonce: random prefix (8 bytes) | chunk counter (uint32 LE)
```

लंबाई फ़ील्ड में GCM टैग शामिल है। हेडर में nonce के अंतिम चार बाइट शून्य होने चाहिए; हर रिकॉर्ड अपना क्रमिक काउंटर इस्तेमाल करता है। `uint32` की सीमा पार होने से पहले काउंटर अस्वीकार किया जाता है, जिससे एक फ़ाइल के भीतर उसका दोबारा शून्य पर लौटना रुकता है।

- **अधूरी फ़ाइल स्वीकार हो सकती है:** अंत के पूरे रिकॉर्ड हटाने पर त्रुटि आना आवश्यक नहीं है। खाली फ़ाइल में प्रमाणीकरण टैग नहीं होता और कुंजी का प्रमाणीकरण भी नहीं हो सकता।
- **मेटाडेटा का अधूरा प्रमाणीकरण:** हेडर की संरचना जाँची जाती है, लेकिन संबद्ध डेटा के रूप में उसका पूर्ण प्रमाणीकरण नहीं होता।
- **फ़ाइलों के बीच nonce टकराव:** यादृच्छिक प्रीफ़िक्स केवल 64 बिट का है। कई फ़ाइलों में एक कुंजी दोहराने से प्रीफ़िक्स टकरा सकते हैं। काउंटर जाँच इस जोखिम को समाप्त नहीं करती।
- **फ़ाइल प्रकाशन:** गंतव्य निर्देशिका में विशिष्ट अस्थायी फ़ाइलें Unix मोड `0600` के साथ बनती हैं; rename से पहले डेटा सिंक किया जाता है और फ़ाइल बंद होती है। विफलता पर सफ़ाई का प्रयास होता है और गंतव्य जानबूझकर नहीं बदला जाता। सफल ऑपरेशन मौजूदा आउटपुट बदल सकते हैं; पहले मूल निर्देशिका बनाएँ और पथ सावधानी से चुनें।
- **ऑपरेटिंग सिस्टम की सीमाएँ:** भरोसेमंद गंतव्य निर्देशिका इस्तेमाल करें। Windows पर उचित ACL चाहिए; rename की परमाण्विकता OS/फ़ाइल सिस्टम पर निर्भर है। निर्देशिका सिंक नहीं होती, इसलिए क्रैश के बाद टिकाऊपन की गारंटी नहीं है। प्रक्रिया क्रैश होने पर अस्थायी फ़ाइलें बच सकती हैं।
- **गोपनीय सामग्री और खतरे:** Go तत्काल मेमोरी मिटाने की गारंटी नहीं देता। यह कोड समझौता किए गए प्रोसेस/OS, स्टोरेज रोलबैक, रीप्ले या मेटाडेटा विश्लेषण से सुरक्षा नहीं देता और E2EE प्रोटोकॉल नहीं है।

केवल AES-GCM इस्तेमाल करने से फ़ाइल प्रारूप सुरक्षित नहीं हो जाता। नए प्रारूप को मेटाडेटा और समापन का स्पष्ट प्रमाणीकरण देना होगा तथा उचित समीक्षा से गुजरना होगा; ये गुण पुराने v1 को पीछे से नहीं दिए जा सकते।

## आर्किटेक्चर और दिशा

डिज़ाइन मॉड्यूलर और हेक्सागोनल सिद्धांतों का अनुसरण करता है: उपभोक्ता विशिष्ट पैकेज इस्तेमाल करते हैं; वैकल्पिक एडेप्टर मूल कॉन्ट्रैक्ट पर निर्भर रहते हैं; मूल भाग अवसंरचना से स्वतंत्र रहता है। इंटरफ़ेस वास्तविक सीमाओं पर बनते हैं, हर फ़ंक्शन के लिए नहीं।

| नियोजित घटक | जिम्मेदारी |
| --- | --- |
| `aead` | प्रमाणित एन्क्रिप्शन और nonce प्रबंधन। |
| `keys` का विस्तार | व्युत्पत्ति, उद्देश्य के अनुसार अलगाव, जीवनचक्र और स्टोरेज एकीकरण। |
| `stream` का प्रतिस्थापन | प्रमाणित फ़्रेमिंग, मेटाडेटा, क्रम और समापन। |
| `envelope` | स्पष्ट संस्करण वाले एन्क्रिप्टेड ऑब्जेक्ट प्रारूप। |
| `securestorage` | एन्क्रिप्टेड स्थिति और वैकल्पिक स्थायी भंडारण एडेप्टर। |
| `identity` / `pki` | डिवाइस पहचान, हस्ताक्षर, क्रेडेंशियल, प्रमाणपत्र और विश्वास सत्यापन। |
| `e2ee` | समीक्षा के बाद चुने गए स्थापित सत्र/समूह प्रोटोकॉल के एडेप्टर। |

विचाराधीन तकनीकों में ChaCha20-Poly1305, HKDF, X25519, Ed25519, Argon2id, MLS और समीक्षित पोस्ट-क्वांटम तंत्र शामिल हैं। ये मूल्यांकन के उम्मीदवार हैं, उपलब्ध क्षमताएँ या नया निजी प्रोटोकॉल बनाने की विधि नहीं। CryptoX संदेश सर्वर, उपयोगकर्ता पंजीकरण, कतारें, पुश डिलीवरी या क्लाउड ऑर्केस्ट्रेशन लागू नहीं करेगा।

## परीक्षण और CI

CryptoX रिपॉज़िटरी से चलाएँ। पहला ब्लॉक Make इस्तेमाल करता है; दूसरे में सीधे कमांड और भेद्यता विश्लेषण शामिल हैं:

```sh
make check
make fuzz
```

```sh
go vet ./...
go test -race -count=1 -coverpkg=./... -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
go test ./stream -run='^$' -fuzz=FuzzDecryptV1 -fuzztime=30s -parallel=2
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
```

परीक्षण `utils` के चार फ़ंक्शन, AES कुंजी लंबाई, खंड सीमाएँ, गलत कुंजियाँ, गलत हेडर/लंबाई, बदले या पुनः क्रमित खंड, खंडित पढ़ाई, अधूरी लिखाई, त्रुटि प्रसार, अस्थायी फ़ाइल सफ़ाई और गंतव्य संरक्षण को जाँचते हैं। समानांतर परीक्षण स्वतंत्र फ़ाइलें इस्तेमाल करते हैं। v1 की ट्रंकेशन सीमा भी स्पष्ट परीक्षण में दर्ज है। फ़ज़िंग विफलता के दौरान आवश्यक शर्तें जाँचती है, केवल panic का अभाव नहीं।

[CI वर्कफ़्लो](.github/workflows/ci.yml) push, pull request, मैन्युअल और साप्ताहिक रन के लिए कॉन्फ़िगर है। इसमें Go `stable` पर Linux/Windows/macOS, Linux पर अतिरिक्त `oldstable` जॉब, कवरेज और JSON आर्टिफ़ैक्ट, फ़ज़िंग तथा `govulncheck` हैं। कॉन्फ़िगरेशन रिमोट सफलता का प्रमाण नहीं: अपने कमिट का रन देखें। कवरेज और सफल परीक्षण स्वतंत्र क्रिप्टोग्राफ़िक समीक्षा का विकल्प नहीं हैं।
